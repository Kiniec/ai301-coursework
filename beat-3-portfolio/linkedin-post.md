I opened a contribution to ChurchCRM, an open-source church management system, after finding that one of its recurring event features was not documented. I updated the documentation to explain how users can schedule events on the 1st through 5th occurrence of a weekday each month and opened a pull request with those changes.
What seemed like a simple documentation task turned into a valuable lesson in verifying details and responding to feedback. I first confirmed the feature was missing from the documentation, then updated two documentation pages and ran project checks to make sure my changes were accurate. After opening the pull request, I received review comments that led me back to the source code to verify how the feature actually worked and to improve the instructions for future users.
The pull request is still open and waiting for human review, but the review comments have been addressed and my project checks passed. The experience reinforced that good documentation is not just about explaining a feature. It is about making sure the next person can find, understand, and use it without having to dig through code themselves.
